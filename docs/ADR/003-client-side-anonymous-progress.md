# ADR-003: Client-Side Anonymous Progress Tracking

## Status
Accepted

## Date
2026-10-02

## Context

Phase 3 introduces user tracking, completion recording, and personal progress metrics to VisuCode. However, full backend infrastructure (PostgreSQL, Prisma, GraphQL) is scheduled for Phase 4.

Scaffolding a custom database or temporary backend API in Phase 3 Sprint 1 would violate the monolith roadmap and risk premature throwaway code. At the same time, naive client-side storage (e.g., components reading `localStorage` directly) creates severe issues:
- SSR hydration mismatches in Next.js App Router.
- State desynchronization between catalog cards, problem views, and profile pages.
- Risk of losing progress on refresh or corrupting data with invalid slugs.
- High refactoring cost when transitioning to authenticated accounts in Sprint 2 and backend GraphQL in Phase 4.

## Decision

1. **Service Layer Encapsulation (`progress.service.ts`)**:
   All progress reads, writes, and subscriptions must flow strictly through `apps/web/lib/services/progress.service.ts` ([`F-P3S1-01`](../phase-3-quality-flags.md)). Components are strictly forbidden from directly calling `localStorage`.

2. **Anonymous Identity Persistence**:
   Progress is keyed in `localStorage` under `visucode_progress_${userId}`, reusing the persistent anonymous UUID (`visucode_uid`) generated by `apps/web/lib/logger.ts`. This ensures structured analytics and progress tracking reference the identical user entity.

3. **Client/Server Service Boundary**:
   Next.js 16 App Router requires strict isolation between server-only and client modules:
   - `problem.service.ts` uses `fs/promises` to read problem JSON files and is strictly server-side.
   - `progress.service.ts` is marked with `'use client'` and contains client-side storage adapters and React hooks.
   - Server Components (`page.tsx`) load problem/pattern data and pass it as props to client components, preventing Node.js server modules from leaking into client browser bundles.

4. **Reactive State via `useSyncExternalStore`**:
   To avoid hydration mismatches and eliminate prop drilling:
   - `useUserProgress()` uses React's native `useSyncExternalStore`.
   - Referential stability is guaranteed via an in-memory snapshot cache (`cachedRawString` and `cachedProgress`), preventing infinite re-render loops.
   - SSR returns a stable `SERVER_DEFAULT_PROGRESS` snapshot.
   - Mutations broadcast to in-memory listeners and cross-tab `window.addEventListener('storage')` events.

5. **Completion Idempotency & Resilience ([`F-P3S1-02`](../phase-3-quality-flags.md))**:
   - `markProblemComplete(slug)` trims inputs, rejects empty/malformed values, and enforces uniqueness with set semantics.
   - Malformed or corrupted storage JSON recovers gracefully to defaults without crashing the application.
   - Dual completion triggers:
     - **Automated**: Passing all test cases in `TestRunner.tsx` auto-marks completion.
     - **Manual**: Explicit `ProblemCompletionToggle` button in the problem page top bar.

6. **Sprint 2 Account Merge Contract**:
   When authentication (Auth.js GitHub/Google) ships in Sprint 2, the anonymous `completedProblems` and `completedLessons` sets will be merged onto the authenticated account using a **lossless set union** (`[...new Set([...anon, ...remote])]`).

## Consequences

- **Zero Backend Required in Sprint 1**: Progress functions immediately for any visitor with zero database cost or latency.
- **Zero Hydration Mismatches**: Seamless rendering between Next.js SSR and client hydration.
- **Single Source of Truth ([`F-P3S1-03`](../phase-3-quality-flags.md))**: Problem page toggle, problem catalog cards, pattern progress badges, and the developer profile (`/profile`) derive from the identical reactive store.
- **Safe Phase 4 Evolution**: When PostgreSQL and GraphQL land in Phase 4, only the internal implementation of `progress.service.ts` needs to be swapped to a remote GraphQL mutation adapter; all UI components remain unchanged.
